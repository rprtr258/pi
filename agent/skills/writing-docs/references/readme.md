# READMEs

The README is the page a stranger lands on. Its job: let a reader decide whether the project is for them, then reach a first working result — in that order.

## Structure

1. **Name and one-line description.** What it is, in the words someone would search for.
2. **What it does, and what it does not do.** The problem it solves and its boundary. A reader who discovers a limitation after installing has been misled.
3. **Install.** The shortest command that works, with prerequisites and supported versions.
4. **Minimal working example.** The smallest complete program that produces a visible result. Copy-pasteable as-is, with no placeholders.
5. **Next steps.** The guide, API reference, or examples for the reader's next question.
6. **License and status.** License, and whether the project is maintained or experimental.

Keep the project's own documentation links in one place rather than repeating them per section.

## Rules

- The first example must actually run. Verify it in a clean environment and state the version you verified.
- Do not inline the full API or a long feature list; link to the reference.
- Show output where the reader needs it to confirm success.
- Keep it in sync with reality: an install command that no longer works is worse than none.
- Show the entry point for the project's shape — a library's import and smallest call, a CLI's one command and its output, a service's way in.
- Badges, screenshots, and ASCII banners either serve the reader or go. A screenshot of CLI output is usually worse than the text it replaced.
